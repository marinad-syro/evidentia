## Problem Statement

People in India can't reliably find the right healthcare provider. Practo, JustDial, and IndiaMART list providers but don't understand clinical needs, don't distinguish trustworthy listings from placeholder aggregator data, and return ranked lists rather than recommendations with reasoning.

This tool accepts a plain-language description of a health need, maps it to the right specialty, finds geographically relevant providers in a 10,000-row India-specific dataset, and returns 3–5 ranked recommendations with an explicit trust score showing exactly why each provider is (or isn't) reliable.

**The "whoa" moment for a demo:** watching the AI reason out loud — "Found 63 ophthalmologists within 10km of Koramangala… narrowing to 25 by clinical match… verifying contact details for top 3…" — in a live streaming progress feed.

**The real product differentiation:** the trust score, computed from structured dataset signals plus live website verification, that tells users not just *who* is nearby but *who is actually trustworthy*.

---

## What Makes This Cool

- **India-specific trust signal layer.** The dataset encodes signals nobody else surfaces: phone number shared across multiple providers (aggregator artifact), whether a website is just Justdial vs. a real domain, whether affiliated staff profiles exist. This is proprietary signal, not star ratings.
- **Transparent reasoning.** Every recommendation card shows the trust score *and* the tooltip explaining what went into it. Not a black box.
- **Natural language in, structured answer out.** "Burning sensation when peeing" → "Urology / General Practice → 3 providers near you." No dropdown, no specialty code, no filter hunting.
- **The caveat line.** LLM-generated per card: "Listed as a 1-doctor clinic — for major procedures consider a hospital." No other finder does this.

---

## Scope (Hackathon Cut)

**In scope:**
- Provider search path end-to-end (NL → specialty → pre-filter → semantic rank → trust score → cards)
- Streaming progress UI (server-sent events or chunked HTTP)
- Trust score from dataset columns + live verification via Tavily Extract API for top 3 (5s timeout, graceful fallback)
- Recommendation cards: name, type, address, distance, phone, matched specialties, trust score with tooltip, LLM-generated "why this one"

**Explicitly out of scope (for hackathon):**
- General healthcare informational KB ("What is glaucoma?") — add post-demo
- User accounts, history, saved providers
- Map view / visual geography
- Mobile-native app (responsive web only)

---

## Premises (all agreed)

1. The streaming UI is the demo hook; the trust score is the real product differentiation.
2. Cutting the informational KB narrows scope without losing demo impact.
3. Live scraping for top 3 providers is included, but with a 5s timeout and silent fallback to dataset-only trust score.

## Architecture — Approach A: Thin Agent, Thick Precompute

```
┌─────────────────────────────────────────────────────────────────┐
│  OFFLINE (run before demo)                                       │
│                                                                 │
│  10K provider CSV                                               │
│    → build embedding index (FAISS or ChromaDB)                 │
│       text per row: "{name} {specialties} {procedures}           │
│                      {capabilities} {description[:500]}"        │
│       (omit fields if null/empty; max 512 tokens per row)       │
│       model: text-embedding-3-small (OpenAI) or                 │
│              all-MiniLM-L6-v2 (local, no API key)              │
│       one 1536-dim (or 384-dim) vector per provider row         │
│    → precompute trust score for all 10K from dataset columns    │
│    → store: provider_db.parquet + embeddings.faiss + trust.json │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  RUNTIME (per query)                                            │
│                                                                 │
│  1. NL INPUT → LLM call (fast, single-turn)                    │
│     Prompt: "Extract specialty, city/area, optional prefs"      │
│     Output: { specialty_id, lat, lon, radius_km, prefs }        │
│                                                                 │
│  2. SEMANTIC RANK (FAISS cosine search over full 10K index)     │
│     Embed clarified query → cosine search over all 10K vectors  │
│     FAISS returns top-N by similarity (search all, not subset)  │
│     Take top 200 candidates (generous margin for post-filter)   │
│                                                                 │
│  3. POST-FILTER (Python, deterministic, no LLM)                 │
│     From top-200 semantic results, filter:                      │
│       - specialties contains extracted_id                       │
│       - haversine(lat, lon, row.lat, row.lon) <= radius_km      │
│       - AND operatorTypeId == pref (if user expressed)          │
│     If result == 0 after filter: expand radius to 25 km, retry  │
│     Take top 25 from filtered results                           │
│                                                                 │
│  4. TRUST SCORE (dataset columns, already precomputed)          │
│     Apply precomputed score to each of top 25                   │
│     Sort by composite formula (see below), take top 3–5         │
│     For top 3: attempt PARALLEL live verification               │
│       Phase A: 3 concurrent Tavily Extract API calls (5s total) │
│         → returns structured page text per officialWebsite URL  │
│       Phase B: 3 concurrent LLM verification calls (async)     │
│         → prompt includes full page text + provider record      │
│         → LLM checks: phone/name/address present, location      │
│           matches, no placeholder images/video, no generic      │
│           template content, no red flags                        │
│         → output: {verified: bool, trust_delta: +10|0|-5,       │
│                    red_flags: [list]}                           │
│         → run all 3 in parallel (concurrent async tasks)        │
│       → if verified: trust_score += trust_delta                 │
│       → if Tavily timeout/fail: skip LLM, use precomputed score │
│       → cache result for 7 days per provider URL                │
│                                                                 │
│  5. LLM CARD GENERATION (single batched call)                   │
│     Prompt per card (max 60 tokens output):                     │
│       "Provider: {name}. Specialties: {specialties}.            │
│        Query match: {matched_query}. Beds: {capacity}.          │
│        In one sentence (max 20 words), explain why this         │
│        provider fits the user's need. Be specific — no generic  │
│        phrases like 'highly recommended' or 'great choice'."   │
│     Rule-based caveats appended after LLM sentence:             │                      │
│       - numberDoctors == 1 → "1-doctor clinic — for major       │
│         procedures consider a larger hospital"                  │
│       - affiliated_staff_presence = FALSE → "Staff profiles     │
│         not found — call ahead to confirm availability"         │
│       - capability/procedure count < 2 → "Limited clinical      │
│         detail listed — verify scope of services by phone"      │
│       - recency_of_page_update > 12 months → "Listing may be   │
│         outdated — confirm current hours and contact details"   │
│                                                                 │
│  6. STREAM RESULTS to frontend via SSE                          │
│     Each pipeline step emits a progress event                   │
│     Final event: full recommendation payload                    │
└─────────────────────────────────────────────────────────────────┘
```

### Specialty Taxonomy Mapping

The dataset uses 560 camelCase specialty tags. Bridge to natural user language:

**Recommended approach:** hybrid — a small lookup table for the most common terms ("eye doctor" → `ophthalmology`, "kids doctor" → `pediatrics`, "skin doctor" → `dermatology`, ~50 entries, built from the dataset's most frequent specialty values) + LLM fallback for everything else. Lookup uses exact lowercased match.

LLM fallback call: "Given this user query, return the single most relevant specialty ID from this list: {complete_specialty_id_list}. Return only the ID string, or null if unclear."

**Validation and ambiguity handling:** After extraction, cross-check the returned tag against the dataset's known specialty_id set. If not found → error: "I couldn't identify a specialty for that. Try: 'eye doctor', 'cardiologist', 'skin specialist'." If LLM returns ambiguous result, pick the specialty_id with the most providers in the dataset. If tied, pick the first alphabetically. Surface the interpretation to the user in the streaming feed: "I interpreted that as [specialty]. [Tap here to choose a different type]."

### Geo Handling

- User gives city name or area → geocode to lat/lon (Nominatim, free, no API key required)
- Default search radius: 10 km
- If no matches within 10 km: expand to 25 km and note in streaming feed ("No results within 10 km — expanding to 25 km…")
- **Geocoding failure fallback:** If Nominatim fails to resolve the location, return error: "Could not find that location. Try a city name instead, e.g. 'Bangalore', 'Mumbai', 'Pune'." Do not fall back to a default location — incorrect geo is worse than no result.

### Trust Score Formula (dataset columns)

| Signal | Weight | Notes |
|--------|--------|-------|
| Valid `officialPhone` (+91 + 10 digits) | +15 | Format validation |
| Phone NOT shared with >3 other providers | +10 | Aggregator artifact detection |
| `officialWebsite` is non-aggregator domain | +15 | Not Justdial/Practo/Facebook |
| Valid `email` format | +5 | Basic format check |
| `description` present, not boilerplate | +10 | Min 50 chars, not all-caps |
| `affiliated_staff_presence` = TRUE | +15 | Real people listed |
| `custom_logo_presence` = TRUE | +10 | Not placeholder |
| `recency_of_page_update` ≤ 12 months | +10 | Active listing |
| `capability` or `procedure` ≥ 2 entries | +10 | Clinical depth |
| **Live scrape bonus** (top 3 only) | +10 | Name + phone confirmed on official site |

Raw max: 110. Scores are clamped to 100 before display and sorting — the live scrape +10 bonus can push a dataset score of 90 to 100, but cannot exceed 100. All signals are independent; null/empty fields contribute 0 points for that signal without affecting others. Scores ≤ 40 show a warning badge.

**Boilerplate detection for `description`:** field must be ≥ 50 chars AND not all-caps AND not an exact match to any of the 5 most common auto-generated templates in the dataset (identify during preprocessing). Phone aggregator check (shared with >3 providers) is a separate signal from format validation.

### Trust Score Composite Ranking Formula

After scoring all 25 shortlisted providers, sort by:

```
final_score = (trust_score / 100) * 0.6 + (1 - min(distance_km, 50) / 50) * 0.4
```

Trust weight: 60%, distance weight: 40%. Distance is normalized against 50 km max (anything beyond 50 km is treated as equally far). This yields a 0–1 score; sort descending, take top 3–5.

### Trust Score Cache TTL

- Dataset-computed scores: computed offline once before demo, stored as `trust.json` keyed by `provider_id`
- `provider_id` = SHA256(name + officialPhone)[:12] — stable across CSV re-sorts, collision-resistant for 10K rows
- FAISS index stores provider_ids at corresponding vector positions so search results map back to providers
- Live-scrape verification: 7-day TTL per provider cached locally (prevents re-scraping the same provider during back-to-back demo runs)
- **Cache behavior at demo time:** On each query, check cache for each top-3 provider. If cache entry exists and age < 7 days, use cached live-scrape result. If stale or absent, attempt fresh scrape (5s timeout). If scrape fails or times out, silently use the precomputed dataset trust score — do not show an error to the user, and do not show a warning badge unless the score is ≤ 40. If all 3 top providers fail live scrape, no banner is shown; the precomputed scores are used without comment.

## Approaches Considered

### Approach A: Thin Agent, Thick Precompute (chosen)
Pre-embed all 10K providers offline. Pipeline runs deterministically at query time. Streaming faked via SSE events that fire as each pipeline stage completes.
- **Effort:** M | **Risk:** Low
- Best for hackathon: fully controllable, demo-resilient

### Approach B: Agentic RAG End-to-End
One LLM agent drives everything via tool calls. No separate pipeline stages.
- **Effort:** M | **Risk:** Med
- Latency unpredictable; harder to control demo pacing

### Approach C: Two-Phase with Live Card Upgrades
Results appear fast with basic info, then trust scores trickle in asynchronously. Cards visually "upgrade" as verification completes.
- **Effort:** L | **Risk:** Med-High
- Impressive UX but significant frontend complexity; risky for demo

## Recommended Approach

**Approach A.** Pre-computed embeddings + deterministic pipeline + SSE streaming.

The streaming progress feed is what makes this demo memorable. Approach A gives full control over the pacing of that feed — each SSE event fires at a real pipeline milestone, so the "thinking out loud" experience is genuine without being unpredictable. Live scraping is isolated to the trust-scoring step for top 3 only, with a timeout that can't derail the demo.

**Frontend stack:** React + Vite. Component structure: `<SearchBar>`, `<ProgressFeed>`, `<ProviderCard>`. SSE via `EventSource` API (native browser). No additional state management library needed — local `useState` is sufficient.

**UI layout (single-page SPA):**
- Top: full-width NL input bar + submit button
- On submit: input collapses, SSE progress feed appears (full width, sequential steps)
- On final SSE event: progress feed collapses, recommendation cards appear (stacked, full width)
- Each card: provider name + type badge + distance tag → address/phone row → trust bar + tooltip → "why this one" + caveat → action buttons (Call / Map / Website)

## Open Questions

1. **Embedding model:** text-embedding-3-small (OpenAI) vs. a sentence-transformers local model. Local is free and avoids API calls at demo time; OpenAI is higher quality but adds a dependency.
2. **Backend language:** Python (FastAPI + FAISS) is the obvious choice given the data pipeline. Confirm before starting.
3. **Specialty taxonomy table:** 50-entry lookup table is enough for the demo — but who builds it? Can pull from the dataset's most common specialty values.
4. **Geocoding:** Nominatim (free, no API key) vs. Google Maps (more accurate, requires key). For a hackathon, Nominatim is fine.

## Error Handling Requirements

| Path | Failure | Handling |
|------|---------|----------|
| NL extraction (LLM) | API timeout / rate limit | try/except → SSE `error` event: "Service temporarily busy — try again in a moment." Return 503. |
| FAISS index at startup | File missing | Startup health check: if `embeddings.faiss` not found, refuse to start with clear log: "Run pre_compute/embed.py first." |
| LLM verification output | Malformed/no JSON | try/except → treat as unverified (trust_delta = 0), continue silently |
| Card generation (LLM) | API failure | try/except → fallback: use first specialty + "Matches your clinical need" as the "why this one" text |
