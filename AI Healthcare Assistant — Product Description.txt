# AI Healthcare Assistant — Product Description

## Overview

An AI assistant that helps people in India find the right healthcare provider for their needs. It interprets the user's symptoms or goals in natural language, asks clarifying questions, and returns a short list of vetted providers (clinics, hospitals, dentists, doctors, pharmacies) with contact details, location, and a confidence score reflecting how trustworthy each provider's listing appears.

The assistant draws on two knowledge bases: a curated set of general healthcare reference documents and a structured dataset of ~10,000 healthcare providers in India.

---

## Knowledge Bases

### 1. General healthcare documents
Used for medical/educational questions ("What is glaucoma?", "When should I worry about chest pain?") and to translate vague user descriptions into clinical terms (e.g. "burning sensation when peeing" → urology / general practice).

### 2. Provider dataset (10,000 rows, India)
Each row is one provider. The columns we plan to use, grouped by how they're used in the pipeline:

**Identity & contact**
- `name`
- `officialPhone`, `phone_numbers` (JSON list)
- `email`
- `officialWebsite`, `websites` (JSON list of all URLs found, including aggregator/social pages)

**Location**
- `address_line1`, `address_line2`, `address_line3`
- `address_city`, `address_stateOrRegion`, `address_zipOrPostcode`
- `latitude`, `longitude` (used as the primary geo key for radius search)

**Classification**
- `operatorTypeId` — private / public

**Clinical match (used for matching the user's need to a provider via semantic search)**
- `specialties` — JSON array of standardized specialty tags (560 distinct values; the primary match column)
- `procedure` — JSON array of free-text procedures performed
- `capability` — JSON array of capability statements
- `equipment` — JSON array (sparse; included for completeness)
- `description` — short free-text summary

**Provider scale**
- `numberDoctors`
- `capacity` (beds)

**Website quality / trust signals**
- `recency_of_page_update`
- `distinct_social_media_presence_count`
- `affiliated_staff_presence` (TRUE / FALSE)
- `custom_logo_presence` (TRUE / FALSE)
- Presence of placeholders instead of videos/pictures (negative)

Columns we are *not* relying on (>98% null or unusable in this dataset): `twitterLink`, `linkedinLink`, `instagramLink`, `affiliationTypeIds`, `number_of_facts_about_the_organization`.

## Workflow

1. **User prompt.** User describes their need in natural language (symptom, condition, type of provider).
2. **Intent routing.** Classify whether the question is informational (route to general healthcare docs) or directional (route to provider search). If directional, continue to step 3.
3. **Clarifying questions.** Ask up to 2–3 targeted follow-ups to nail down: required specialty, city/area. Stop asking once we have these basics, but do note any additional info that can be used in semantic search.
4. **Hard pre-filter (deterministic, no LLM).** Filter the dataset on:
   - `specialties` matches required specialty
   - `facilityTypeId` matches required provider type
   - Within a configurable radius of the user's `latitude`/`longitude` (haversine on the row's lat/lon)
   - `operatorTypeId` if user expressed a preference
   This typically reduces 10,000 candidates to <500.
5. **Semantic rank.** Embed the user's clarified query and rank remaining candidates by cosine similarity against pre-computed embeddings built from `name + description + specialties + procedure + capability`. Take top ~25.
6. **Trust scoring.** For each shortlisted provider:
   - If a fresh trust score is cached (< N days old), use it.
   - Otherwise compute one from the dataset columns (see "Trust score" below). For the top ~5 candidates, also run a live verification pass: scrape the official website (cross-reference name, phone, address, listed specialties against the dataset)
   - Cache the resulting score with a timestamp.
7. **Recommendation.** Return the top 3–5 providers with name, address, phone, distance, matched specialty, and trust score. Surface caveats where relevant ("listed as a 1-doctor clinic — for major procedures consider a hospital").

---

## Trust Score

Combines structured signals from the dataset with live verification.

**From the dataset:**
- + has a valid `officialPhone` (Indian `+91` + 10 digits)
- + has a non-aggregator `officialWebsite` (i.e. not just a Justdial/IndiaMART/Practo/Facebook page)
- + has a valid-format `email`
- + `description` present and not boilerplate
- + `affiliated_staff_presence` = TRUE
- + `custom_logo_presence` = TRUE
- + `recency_of_page_update` within the last 12 months
- + `capability` or `procedure` has ≥ 2 entries
- − `officialPhone` shared with multiple other providers (placeholder/aggregator artifact)
- − `websites` are 100% aggregator/social with no real domain
- − `email` format invalid

## UI

The user sees a continuous, transparent progress feed while the agent works. Examples:

- "Understanding your symptoms…"
- "Looking for ophthalmologists within 10 km of Pune…"
- "Found 47 candidates — narrowing down to the best matches…"
- "Scoring providers based on reliability…"
- "Verifying contact details for the top 3 by phone…"
- "Done. Here are 3 providers I'd recommend."

Each recommendation card shows: provider name, facility type, address with distance, primary phone, matched specialties, trust score (with a tooltip explaining what went into it), and a one-line "why this one" summary generated by the LLM.

## Open questions / things to confirm with G-Stack

- **Trust-score cache TTL.** How fresh do verifications need to be — 7 days, 30 days, 90 days?
- **Specialty taxonomy mapping.** The dataset uses 560 specialty tags in camelCase. We'll need a mapping table from common user phrases ("skin doctor", "kids doctor", "eye specialist") to specialty IDs. OR we can live it up to the LLM to infer the needed specialist when the link is that obvious.
- **Geo defaults.** What's the default search radius, and how do we handle users who give a city name vs. allow location access?
